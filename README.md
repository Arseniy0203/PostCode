# ПочтаТех — квартальное PI-планирование и звёздная карта компетенций

Сервис раскладывает бэклог ИТ-работ по 6 спринтам квартала с учётом ёмкости команд
в Story Points, часов ролей, стека и зависимостей; каждые две недели по факту
пересчитывает хвост плана, подсвечивает риски и KPI; показывает, на ком держатся
компетенции (Bus Factor), кого нанять и кого обучить.

## Быстрый старт

Нужен Python 3.11+.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
streamlit run frontend/app.py        # из корня репозитория
```

В интерфейсе загрузите датасет `data/raw/Хакатон_датасетс_правками_по_списку_вопросов_1.xlsx`
как Неделю 0, затем по очереди файлы факта спринтов из `demo_scenarios/<сценарий>/Sprint_N_Fact.xlsx`.
Загруженный спринт можно **заменить** или **удалить** кнопками в боковой панели: при замене
следующие спринты пересчитываются заново по уже загруженным файлам; файл с номером другого
спринта в имени не применяется без подтверждения.

Прочее:

```bash
pytest -q                                          # 196 тестов, включая инварианты плана на реальных данных
python -m backend.ingestion.parse_dataset          # пересобрать data/processed/*.json из Excel
python -m backend.ingestion.parse_dataset my.xlsx  # из другого файла (например, скрытого датасета)
python sprint.py                                   # пересобрать демо-факты в demo_scenarios/
```

Без интерфейса весь отчёт получается одной функцией:

```python
from backend.recalculation.pipeline import run_quarter
report = run_quarter("key_task_delay", until_sprint=3)   # 0 — только Неделя 0
report["plan"], report["alerts"], report["kpi"], report["hiring_roadmap"], report["starmap"]
```

Если в консоли Windows кракозябры — `set PYTHONIOENCODING=utf-8`.

## Демо за 5 минут

1. **Неделя 0.** Загрузить датасет. В квартал входит 36 задач из 37: 11 — до полной цели,
   остальные — с частичной целью из справочника «Варианты выбора цели», потому что в
   компании нет ни одного Руководителя проекта, специалиста поддержки и 1С. По строгому
   правилу «нет роли — задачу не берём» вошло бы только 10 задач, а 5–6 спринты
   остались бы пустыми. Ёмкость команд по SP загружена до лимита — это и есть «намеренный
   дефицит» из условия.
2. **«Всё сразу или по плану»** — подсказка организаторов в цифрах: если запустить все 37
   задач в спринте 1, каждая команда перегружена по SP (до 625% у Team-Platform), ДевОпс
   и Архитектор решений нужны в 4–5 раз больше своего фонда; план держит загрузку каждого
   спринта не выше 100% ёмкости и берёт 36 задач против 10 по строгому правилу.
3. **Карточка задачи** — решение, код причины из справочника, цель, цифры, рекомендация
   («нанять РП — тогда до полной цели»), кто и в каком спринте работает.
4. **Scenario_2_Cascade_Delay**, факты спринтов 1–3: ключевая задача не закрылась → жёлтый
   каскадный алерт с цепочкой зависимых задач; он держится, пока цепочка отстаёт от baseline.
5. **Scenario_3_Canceled_Task**: заказчик отменил SRV-4041 → красный алерт на зависимую
   SRV-4042, PI Predictability падает.
6. **Scenario_1_Ideal**: всё по плану — ни одного сдвига и ни одного красного/жёлтого алерта
   за 6 спринтов (пересчёт воспроизводит собственный план).
7. **Звёздная карта** — Bus Factor внутри каждой команды, «нанять Руководителя проекта
   (449 ч, 25 задач)», «обучить ENG-429 (Java, знает Docker/Kubernetes) на ДевОпс —
   сейчас 20 задач держатся только на ENG-419».

## Архитектура

```
data/raw/*.xlsx ──► backend/ingestion   парсинг листа, нормализация, валидация
                     backend/planning    планировщик: приоритетное списочное планирование
                     backend/recalculation  baseline, пересчёт по факту, сценарии, найм,
                                           итоги квартала, бэклог следующего квартала
                     backend/risk        алерты red/yellow/orange + info, качество данных
                     backend/kpi         PI Predictability, Say/Do
                     backend/starmap     профили, Bus Factor (компания и команды), нанять/обучить

```

Контракты данных — `contracts/*.md`, допущения — `docs/assumptions_draft.md`.

## Модель планирования

- **Квартал** — 6 спринтов по 2 недели с 01.07.2026: S1 01.07–14.07 … S6 09.09–22.09
  (эксперты: квартал календарный).
- **Бэклог** — задачи ToDo и InProgress; Done в квартал не берутся (эксперты). Задачи в
  работе планируются на остаток: смета − факт из Spent_time_roles.
- **Смета** — калькулятор сметы по ролям (эксперты: целевая смета); `estimated_hh` из Tasks
  при расхождении помечается некорректным в отчёте о качестве данных.
- **Ёмкость команды** = средний `velocity_achieved` × 0.8 SP на спринт. SP задачи
  списываются по спринтам пропорционально выполненным часам, поэтому задача крупнее
  спринтовой ёмкости растягивается, а не выпадает (SRV-4012: 13 SP при 10.8). Ёмкость —
  жёсткий лимит: сумма SP команды в спринте не превышает её.
- **Часы инженера** = 80 × `capacity_rate` на каждую его команду: парттаймер 0.5 + 0.5 даёт
  по 40 ч каждой команде и не больше 80 ч всего.
- **Люди** — сначала своя команда, затем та же роль из других команд, если свои заняты
  (кого привлекли — пишется в причине). Роли нормализуются: «ДевОпс»/«Девопс», «iOS»/«IOS».
- **Стек** — если технология из названия задачи есть у кого-то из носителей роли, на эту
  роль берутся только они (пример PDF: Big Data + Python).
- **Зависимости** — все три типа связей значат «A блокирует B»; B начинается не раньше
  спринта, следующего за окончанием A. Циклы называются в причине.
- **Порядок** — топологический; среди доступных: задачи в работе, затем скоринг
  `rung × (1 + 0.5 × число блокируемых задач)`. При пересчёте очередь обязательств не
  перетасовывается — новые задачи заполняют оставшуюся ёмкость.
- **Роли без людей** (эксперты: «нет ресурсов — переносим + рекомендация, в т. ч. частичная
  цель»): работа доступных ролей планируется, недостающие часы выносятся в дефицит, цель
  понижается: нет только руководителя/поддержки → «4. Функционал реализован и готов к ИТ»,
  нет исполнителей части функционала → «3. Функционал реализован частично». Если на
  недостающие роли приходится больше 50% сметы — задача переносится («не будет взято в
  квартал»). То же, если роль есть, но её часы до конца квартала заняты. Строгий режим
  (`missing_roles="postpone"`) оставлен для сравнения.
- **Причины** — у каждой задачи код из справочника «Причины расхождения планов», цель из
  «Вариантов выбора цели», текст с цифрами, факты (`reason_facts`) и рекомендация.

## Пересчёт и риски

- **baseline** фиксируется на Неделе 0 и больше не меняется — от него считаются KPI и сдвиги;
  **current** пересчитывается после каждого факта, прошедшие спринты заморожены.
- Факт — строго следующий спринт (защита от повторной подачи), ошибочный факт отменяется
  `rollback`. Файл факта — датасет с накопленными часами; уже учтённое вычитается.
- Алерты (обязательные по условию):
  🔴 **красный** — прогноз окончания за 6-м спринтом или задача выпала из плана Недели 0;
  🟡 **жёлтый** — задача позже baseline и сдвигает цепочку зависимых;
  🟠 **оранжевый** — потребность роли на спринт больше фонда всех её сотрудников; роли нет в
  компании (нанять, со сроками: поиск ≈ 3 спринта + адаптация 50%/75%); задача не влезла.
  Плюс info: блокировки с корневой причиной, перерасход сметы, зависшие задачи, KPI,
  единственный носитель роли (с кандидатом в дублёры), качество данных.
  У алертов жизненный цикл: новый → держится → решён.
- **KPI**: PI Predictability = завершённые PRODF / обещанные на Неделе 0 (норма 80–100%),
  Say/Do = сделано SP / запланировано на спринт (норма 90–105%); пустые и будущие спринты
  — «нет данных», а не 0%.
- **Что если**: план найма по шагам («1. Нанять РП → +8 задач до полной цели…»), бэклог
  следующего квартала с датой начала поиска людей.

## Звёздная карта

Bus Factor = число людей, владеющих компетенцией (парттаймер считается один раз). Уровни:
роль из сметы и её ключевой стек. Считается **внутри каждой команды** (эксперты) и по
компании. Показывает, что встанет без конкретного человека, кого нанять (роли с BF = 0) и
кого обучить (у кандидата уже есть ключевой стек роли или навыки единственного носителя).

## Данные и их аномалии

Актуальный датасет — `Хакатон_датасетс_правками_по_списку_вопросов_1.xlsx` (правки
организаторов по вопросам команд). Обрабатываются: съехавший заголовок Task_dependencies
(связи читаются по позиции, шапка отбрасывается по содержимому), задачи-призраки и дубли
связей (в отчёт о качестве данных, из планирования исключаются), разные написания ролей,
числа с запятой, `capacity_rate` строкой, расхождения сметы, роли без единого инженера.
Таблицы ищутся по маркерам, поэтому их порядок на листе не важен; без обязательных колонок
парсер падает с понятной ошибкой, а не выдаёт битые данные.

## Проверка на других данных

Ничего не зашито под конкретный датасет: ID задач, команды, роли и состав инженеров
читаются из файла, константы — в конфиге. Решение прогнано на 12 сгенерированных
датасетах с другими задачами, командами, зависимостями и velocity (план без перегрузок,
у каждой задачи есть причина решения, при работе по плану нет сдвигов и красных алертов)
и на 13 испорченных файлах (чужой Excel, переименованные листы, пустые и нечисловые
значения, формулы вместо ID) — падений нет, отказ объясняется по-русски.
