# ПочтаТех — квартальное PI-планирование и звёздная карта компетенций

Сервис раскладывает бэклог ИТ-работ по 6 спринтам квартала с учётом ёмкости команд
в Story Points, часов ролей, стека и зависимостей; каждые две недели по факту
пересчитывает хвост плана, подсвечивает риски и KPI; показывает, на ком держатся
компетенции (Bus Factor), кого нанять и кого обучить. Результат выгружается файлом:
Excel с заполненными колонками датасета и печатный PDF.

## Развёрнутый сервис

**https://pochtatech-pi-planner.streamlit.app/** — тот же код, что в этом репозитории,
ничего устанавливать не нужно. Первый заход после простоя будит приложение (около минуты).

## Демо за одну кнопку

Чтобы увидеть продукт, файл не нужен. На стартовом экране — кнопка
**«Открыть пример на демо-данных»**: она поднимает рассчитанный квартал целиком —
Неделю 0 и все шесть спринтов. Первый запуск считает квартал (до минуты), дальше
сценарии переключаются из кэша.

В боковой панели вместо загрузки файлов два переключателя:

- **«Сценарий квартала»** — «Всё по плану», «Задержка ключевой задачи», «Уход инженера».
  Факты спринтов в демо получаются симуляцией по нашему же плану
  (`backend/recalculation/scenarios.py`): задача и инженер для сценария выбираются по
  структуре плана, а не по зашитым ID.
- **«Срез данных»** — от «Снимок (Baseline Неделя 0)» до «После Спринта 6»; цифры на всех
  страницах пересчитываются. При смене сценария выбранный срез сохраняется — удобно
  сравнить один и тот же спринт в разных сценариях.

Что видно в каждом сценарии:

| Сценарий | Что происходит | Что увидеть |
| --- | --- | --- |
| Всё по плану | Каждая задача закрывается в свой плановый спринт | За 6 спринтов ни одного красного и жёлтого алерта, Say/Do 100% в каждом спринте — пересчёт воспроизводит собственный план |
| Задержка ключевой задачи | В спринте 1 не продвинулась SRV-4011 — задача, от которой зависит больше всего задач плана | Жёлтый каскадный алерт с цепочкой зависимых задач держится, пока цепочка отстаёт от baseline (спринты 1–4); на 6-м спринте Say/Do 287,5% с подписью «23 из 8 SP плана» — команда догнала хвост |
| Уход инженера | После спринта 1 уходит ENG-419 — единственный в компании ДевОпс | 4 красных алерта, прогноз PI Predictability падает со 100% до 80% |

Выйти из демо — кнопка **«Выйти из демо и загрузить свой файл»**. Данные демо —
`data/processed/*.json` из репозитория; в демо нельзя загружать факты и снимать задачи
вручную, потому что снимки посчитаны заранее.

## Быстрый старт

Нужен Python 3.11+ (проверено на 3.13). Всё локально: ни базы, ни внешних сервисов.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
streamlit run frontend/app.py        # из корня репозитория
```

Прочее:

```bash
pytest -q                                          # 210 тестов, включая инварианты плана на реальных данных
python -m backend.ingestion.parse_dataset          # пересобрать data/processed/*.json из Excel
python -m backend.ingestion.parse_dataset my.xlsx  # из другого файла (например, скрытого датасета)
python sprint.py                                   # пересобрать демо-факты в demo_scenarios/
```

Без интерфейса весь отчёт получается одной функцией:

```python
from backend.recalculation.pipeline import run_quarter
report = run_quarter("key_task_delay", until_sprint=3)   # 0 — только Неделя 0
report["plan"], report["alerts"], report["kpi"], report["hiring_roadmap"], report["starmap"]
```

Если в консоли Windows кракозябры — `set PYTHONIOENCODING=utf-8`.

## Работа на своём файле

1. **Неделя 0.** На стартовом экране загрузить мастер-датасет:
   `data/raw/Хакатон_датасетс_правками_по_списку_вопросов_1.xlsx` или свой файл того же
   формата. Нет файла — кнопка **«Скачать шаблон датасета»** даёт пустую структуру
   (см. «Что можно забрать из сервиса»). Построится план квартала, откроется обзор.
2. **Факт спринта.** В боковой панели — загрузчик «Загрузить факт Спринта N»; доступен
   только следующий по порядку спринт. Принимаются два формата:
   - **бланк факта** — кнопка «Бланк факта спринта N (заполнен планом)» рядом с загрузчиком;
   - **датасет с накопленными часами** — как файлы `demo_scenarios/<сценарий>/Sprint_N_Fact.xlsx`;
     уже учтённые часы вычитаются, в пересчёт идут часы именно за этот спринт.
3. **Исправить ошибку.** Загруженный спринт можно **заменить** или **удалить**: при замене
   следующие спринты пересчитываются заново по уже загруженным файлам, при удалении
   убираются этот спринт и все следующие.
4. **Защита от путаницы файлов.** Факты сделаны в том же формате, что и мастер-датасет,
   поэтому их легко перепутать. Сервис не применяет без подтверждения («Всё равно
   загрузить») мастер-датасет в слот спринта, файл, уже загруженный за другой спринт,
   и файл с другим номером спринта в имени. На стартовом экране так же
   предупреждает, если вместо мастер-датасета подали файл, похожий на факт спринта.

Готовые факты для ручной проверки — `demo_scenarios/`:
`Scenario_1_Ideal` (всё по плану), `Scenario_2_Cascade_Delay` (задержка SRV-4011),
`Scenario_3_Canceled_Task` (в спринте 1 заказчик отменяет SRV-4041 → красные алерты по
SRV-4041 и зависимой SRV-4042, прогноз PI Predictability 93,3%).

## Разделы интерфейса

Семь разделов в левом меню; до загрузки датасета или запуска демо открыта только главная.

| Раздел | Что в нём |
| --- | --- |
| Главная | Старт: загрузка датасета, шаблон, демо-режим |
| Обзор квартала | Метрики, старт задач по спринтам, выполнение плана (исходный план, прогноз, факт), команды с составом при наведении, что требует внимания |
| Квартальный план | Сетка шести спринтов, поиск задачи, карточка с причиной и расчётом, выгрузка, ручные решения |
| Показатели KPI | PI Predictability и Say/Do с расшифровкой по инициативам и спринтам |
| Загрузка команд | Сравнение «всё сразу» с планом по SP и по часам ролей, тепловая карта спринтов |
| Риски и алерты | Критические, каскадные, ресурсные, наблюдения и качество данных; фильтр по команде |
| Звёздная карта | Граф компетенций, Bus Factor по командам, кого нанять и кого обучить |

Во всех разделах, кроме главной, сверху четыре карточки: задачи в квартале, PI Predictability (до конца
квартала — прогноз), Say/Do последнего спринта с абсолютными SP рядом с процентом и
число команд. До загрузки фактов Say/Do показывает «—», а не прогноз. Графики
переключаются в таблицу и обратно.

**Карточка задачи** раскрывается на месте — в сетке спринта или из поиска: решение,
причина из справочника, цель в квартале, сроки, обоснование с цифрами, что можно
сделать; ниже — «Расчёт, на котором основано решение» (нужно и доступно часов, ёмкость
команды, место в очереди, привлечённые из других команд), риски по задаче, часы по ролям
с пометкой «нет исполнителя», «Кто и когда работает» по спринтам и зависимости.

Оформление — Soft UI Dashboard 3: стили в `frontend/assets/soft-ui.css`, оригинальные
изображения и лицензия шаблона — в `frontend/assets/soft-ui/`.

## Что можно забрать из сервиса

Выгрузка — ответ на требование кейса заполнить колонки датасета: результат планирования
выходит за пределы экрана и уходит на PI-планирование файлом.

- **Excel с планом** — кнопка «Скачать Excel» на странице «Квартальный план». Лист «План» —
  те же задачи, что в датасете, но с заполненными колонками `плановый результат`,
  `будет включено в спринт` и `исполнитель`: в исходном датасете они пусты у всех
  незакрытых задач. У задачи квартала там цель из справочника, спринты и инженеры с
  часами; у перенесённой — «не будет взято в квартал». Рядом — решение, причина, что
  сделать, часы сметы и часы без исполнителей, зависимости. Кроме того: лист «Сводка»,
  лист на каждую команду, «Алерты» и «Нанять и обучить». Выгружается срез, выбранный в
  боковой панели, и задачи, отобранные фильтрами страницы: выберите команду — в файле
  останется только она и её алерты.
- **PDF-отчёт** — кнопка «Скачать PDF» там же. Печатная версия: сводка по кварталу,
  страница на каждую команду, риски и план найма. Кириллица — шрифты DejaVu из
  `backend/export/fonts/`.
- **Шаблон датасета** — кнопка «Скачать шаблон датасета» на стартовом экране: пустой файл
  со структурой организаторов — маркеры таблиц, заголовки колонок, список ролей
  калькулятора сметы и справочники, без строк данных. Заполняется своими данными и
  загружается обратно; пустой шаблон сервис отклоняет человеческим текстом, а не
  трассировкой.
- **Бланк факта спринта** — кнопка в боковой панели. В файле уже проставлены задачи
  спринта, ожидаемый статус и часы по ролям из плана, второй лист — инструкция: команде
  остаётся отметить отклонения. Загруженный без изменений, он не даёт ни одного красного
  или жёлтого алерта — факт совпал с планом.

## Ручные решения руководителя

PI-планирование — это переговоры: планировщик предлагает, решает человек. В карточке
любой незакрытой задачи есть кнопка **«Снять с квартала»**: указывается причина
(«попадёт в план и выгрузку»), план пересобирается с Недели 0, освободившаяся ёмкость
достаётся другим задачам, уже загруженные факты применяются заново. Над фильтрами
появляется плашка со списком снятого и причинами; причина попадает в карточку задачи и
в колонку «Причина» выгрузки.

Вернуть задачу можно в её карточке («Вернуть в планирование») или все сразу кнопкой
**«Вернуть все в планирование»**. Снятие меняет и план Недели 0 — это решение до
фиксации обязательств, поэтому красным алертом оно не считается. Работает на своём
датасете; в демо кнопок нет.

## Что показать за 7 минут

Всё ниже — в демо-режиме, без файлов.

1. **Неделя 0, «Обзор квартала».** В квартал входит 36 задач из 37: 11 — до полной цели,
   25 — с частичной целью из справочника «Варианты выбора цели», потому что в компании
   нет ни одного руководителя проекта, специалиста поддержки и специалистов 1С. По строгому
   правилу «нет роли — задачу не берём» вошло бы только 10 задач, а 5–6 спринты остались бы
   пустыми.
2. **«Загрузка команд».** Подсказка организаторов в цифрах: если запустить все 37 задач в
   спринте 1, перегружена каждая из 6 команд — до 625% у Team-Platform, ДевОпс и Архитектор
   решений нужны в 4–5 раз больше своего фонда за спринт, у шести ролей нет ни одного
   человека. План держит загрузку каждого спринта не выше 100% ёмкости.
3. **«Квартальный план», карточка задачи.** Решение, код причины из справочника, цель,
   расчёт, рекомендация («нанять руководителя проекта — тогда до полной цели»), кто и в
   каком спринте работает. В поиске — `SRV-4043`, единственная перенесённая задача (ниже —
   почему).
4. **Сценарий «Задержка ключевой задачи», срез «После Спринта 1».** SRV-4011 не
   продвинулась → жёлтый каскадный алерт с цепочкой зависимых задач. Срез «После
   Спринта 6» — Say/Do 287,5% и «23 из 8 SP плана»: команда закрыла хвост.
5. **Сценарий «Уход инженера», «После Спринта 1».** Уходит ENG-419, единственный ДевОпс:
   4 красных алерта, прогноз PI Predictability — 80% вместо 100%.
6. **Сценарий «Всё по плану».** Ни одного сдвига и ни одного красного или жёлтого алерта за
   6 спринтов.
7. **«Звёздная карта».** Bus Factor внутри каждой команды, «нанять руководителя проекта
   (449 ч, 25 задач)», «обучить ENG-429 (Java, знает Docker и Kubernetes) на ДевОпс —
   сейчас 20 задач держатся только на ENG-419».
8. **Выгрузка.** Excel и PDF со страницы плана — заполненный датасет и печатный отчёт.

## Модель планирования

- **Квартал** — 6 спринтов по 2 недели с 01.07.2026: S1 01.07–14.07 … S6 09.09–22.09
  (эксперты: квартал календарный).
- **Бэклог** — задачи ToDo и InProgress; Done в квартал не берутся (эксперты). Задачи в
  работе планируются на остаток: смета − факт из Spent_time_roles.
- **Смета** — калькулятор сметы по ролям (эксперты: целевая смета); `estimated_hh` из Tasks
  при расхождении помечается некорректным в отчёте о качестве данных.
- **Ёмкость команды** = средний `velocity_achieved` × 0.8 SP на спринт. SP задачи
  списываются по спринтам пропорционально выполненным часам, поэтому задача крупнее
  спринтовой ёмкости растягивается, а не выпадает (SRV-4012: 13 SP при 10.8). Ёмкость —
  жёсткий лимит: сумма SP команды в спринте не превышает её.
- **Часы инженера** = 80 × `capacity_rate` на каждую его команду: парттаймер 0.5 + 0.5 даёт
  по 40 ч каждой команде и не больше 80 ч всего.
- **Люди** — сначала своя команда, затем та же роль из других команд, если свои заняты
  (кого привлекли — пишется в причине). Роли нормализуются: «ДевОпс»/«Девопс», «iOS»/«IOS».
- **Стек** — если технология из названия задачи есть у кого-то из носителей роли, на эту
  роль берутся только они (пример PDF: Big Data + Python).
- **Зависимости** — все три типа связей значат «A блокирует B»; B начинается не раньше
  спринта, следующего за окончанием A. Циклы называются в причине.
- **Порядок** — топологический; среди доступных: задачи в работе, затем скоринг
  `rung × (1 + 0.5 × число блокируемых задач)`. При пересчёте очередь обязательств не
  перетасовывается — новые задачи заполняют оставшуюся ёмкость.
- **Роли без людей** (эксперты: «нет ресурсов — переносим + рекомендация, в т. ч. частичная
  цель»): работа доступных ролей планируется, недостающие часы выносятся в дефицит, цель
  понижается: нет только руководителя/поддержки → «4. Функционал реализован и готов к ИТ»,
  нет исполнителей части функционала → «3. Функционал реализован частично». Если на
  недостающие роли приходится больше 50% сметы — задача переносится («не будет взято в
  квартал»). То же, если роль есть, но её часы до конца квартала заняты. Строгий режим
  (`missing_roles="postpone"`) оставлен для сравнения.
- **Почему 36, а не 37.** SRV-4043 переносится не из-за ёмкости, а по нашему правилу: 69% её
  часов — Разработчик 1С, Аналитик 1С и Специалист поддержки 1С, которых в компании нет.
  Мы сознательно не берём задачу, где больше половины работы делать некому: это была бы
  треть работы под видом результата. Если ослабить правило, в квартал помещаются все 37.
  Вместо этого — перенос с причиной и рекомендацией нанять.
- **Причины** — у каждой задачи код из справочника «Причины расхождения планов», цель из
  «Вариантов выбора цели», текст с цифрами, факты (`reason_facts`) и рекомендация.
- **Почему эвристика, а не оптимизатор.** Задача раскладки NP-трудная, но упираемся мы не в
  её качество: пик загрузки команд по плану — ровно 100%, плотнее не упакуешь. Узкое место —
  отсутствующие роли, и его оптимизатор не решит. Эвристика же даёт объяснимую причину
  каждого решения и место задачи в очереди.

## Пересчёт и риски

- **baseline** фиксируется на Неделе 0 и больше не меняется — от него считаются KPI и сдвиги;
  **current** пересчитывается после каждого факта, прошедшие спринты заморожены.
- Факт — строго следующий спринт (защита от повторной подачи), ошибочный факт отменяется
  `rollback` (в интерфейсе — «Заменить» и «Удалить»). Факт в формате датасета — с
  накопленными часами; уже учтённое вычитается.
- Алерты (обязательные по условию). Цвет на экране совпадает в легенде, счётчике и полосе
  карточки; тройка подобрана так, чтобы различаться и при дальтонизме:
  - **критический** (красный, в схеме `red`) — прогноз окончания за 6-м спринтом или задача
    выпала из плана Недели 0;
  - **каскадный** (янтарный, `yellow`) — задача позже baseline и сдвигает цепочку зависимых;
  - **ресурсный** (синий, `orange`) — потребность роли на спринт больше фонда всех её
    сотрудников; роли нет в компании (нанять, со сроками: поиск ≈ 3 спринта + адаптация
    50%/75%); задача не влезла.

  Плюс наблюдения (`info`): блокировки с корневой причиной, перерасход сметы, зависшие
  задачи, KPI вне нормы, единственный носитель роли (с кандидатом в дублёры) — и отдельная
  вкладка «Качество данных». В карточке алерта два блока: «Что происходит» и «Что сделать»;
  длинные списки задач свёрнуты. У алертов жизненный цикл: новый → держится → решён.
- **KPI**: PI Predictability = завершённые PRODF / обещанные на Неделе 0 (норма 80–100%),
  Say/Do = сделано SP / запланировано на спринт по baseline (норма 90–105%); пустые и
  будущие спринты — «нет данных», а не 0%. Say/Do выше 100% — команда сделала больше, чем
  обещала на спринт: подтянула работу вперёд или план спринта был занижен; отклонение
  вверх — такой же повод уточнить план, как и вниз. Поэтому рядом с процентом всегда
  показаны абсолютные SP.
- **Что если**: план найма по шагам («1. Нанять РП → +8 задач до полной цели…»), бэклог
  следующего квартала с датой начала поиска людей (в отчёте `run_quarter`).

## Звёздная карта

Bus Factor = число людей, владеющих компетенцией (парттаймер считается один раз). Уровни:
роль из сметы и её ключевой стек. Считается **внутри каждой команды** (эксперты) и по
компании. Показывает, что встанет без конкретного человека, кого нанять (роли с BF = 0) и
кого обучить (у кандидата уже есть ключевой стек роли или навыки единственного носителя).

На графе звёзды — компетенции, точки — инженеры; сплошная красная звезда держится на одном
человеке, пустая с красным контуром не имеет носителей вовсе. Под графом — выбор
компетенции под риском со списком зависимых задач, блок «Что делать» (нанять / обучить),
все варианты переобучения по смежным специальностям и таблица Bus Factor внутри команды.

## Данные и их аномалии

Актуальный датасет — `Хакатон_датасетс_правками_по_списку_вопросов_1.xlsx` (правки
организаторов по вопросам команд). Обрабатываются: съехавший заголовок Task_dependencies
(связи читаются по позиции, шапка отбрасывается по содержимому), задачи-призраки и дубли
связей (в отчёт о качестве данных, из планирования исключаются), разные написания ролей,
числа с запятой, `capacity_rate` строкой, расхождения сметы, роли без единого инженера,
ID задач формулами `=B24` в файле без сохранённых значений.
Таблицы ищутся по маркерам, поэтому их порядок на листе и имя листа не важны; без
обязательных колонок парсер падает с понятной ошибкой, а не выдаёт битые данные.

## Проверка на других данных

Ничего не зашито под конкретный датасет: ID задач, команды, роли и состав инженеров
читаются из файла, константы планирования вынесены в начало модулей
(`backend/planning/scheduler.py`, `backend/planning/capacity.py`,
`backend/recalculation/quarter.py`). Решение прогнано на 12 сгенерированных
датасетах с другими задачами, командами, зависимостями и velocity (план без перегрузок,
у каждой задачи есть причина решения, при работе по плану нет сдвигов и красных алертов)
и на 13 испорченных файлах (чужой Excel, переименованные листы, пустые и нечисловые
значения, формулы вместо ID) — падений нет, отказ объясняется по-русски.

