## Преобразование данных

Решения подтверждены организаторами (встреча 21.09.2026):

- **Квартал: 01.07.2026 — 23.09.2026**, 6 спринтов по 2 недели. Номер спринта
  считается от 01.07.2026. Проверка по датасету: это единственное окно, где
  задачи ToDo и начинаются, и заканчиваются внутри квартала (11 шт.), и ни одна
  незавершённая задача не выходит за его пределы.
- **Завершённые задачи (Done) в квартал не берутся.** 8 задач со статусом Done —
  факт прошлых периодов, в baseline и в знаменатель KPI они не попадают.
- 26 из 37 незавершённых задач имеют `planned_start` раньше 01.07.2026
  (самая ранняя — 10.12.2025): на Неделе 0 они уже просрочены и ставятся
  в спринт 1. Исходные даты сохраняются в полях `*_date`.
- **Источник истины по трудозатратам — калькулятор сметы**, а не колонка
  `estimated_hh` в блоке Tasks. Она заполнена некорректно: у ONK-2475 (276
  против 256), MOB-7011 (180 против 165), DB-203 (80 против 72) и SRV-4012
  (240 против 270). Парсер перезаполняет поле суммой по ролям и логирует
  расхождение, чтобы оно было видно в интерфейсе.
- У KP-3898, SRV-4012, SRV-4014 и SRV-4016 строка «Итого по ролям» в калькуляторе
  не сходится с суммой ролей: итог пересчитывается по колонке ролей.
- **Названия ролей нормализуются**: «Девопс» = «ДевОпс», «Разработчик IOS» =
  «Разработчик iOS», «Разработчик BigData» = «Разработчик Big Data».
  Нормализация общая для парсера, планировщика и звёздной карты.

## Дефицит ресурсов в датасете (замер на 21.09.2026)

За весь квартал суммарного дефицита почти нет: спрос 240 SP против ёмкости
329 SP, по часам ролей — например, Java 1507 из 3360 ч. Дефицит проявляется
внутри спринтов (лимит 80 ч на инженера при ставке 1.0, зависимости,
растягивание задач) и у ролей без носителей: Руководитель проекта (455 ч),
Разработчик 1С (107 ч), Специалист поддержки (64 ч), роли 1С.
Единственная команда с нехваткой SP за квартал — Team-Platform (45 из 43.2).

## Правила приоритизации

- Если ресурсов нет, задача в квартал не берётся: решение `postponed`
  с кодом `NO_RESOURCES` (подтверждено организаторами).
- К причине переноса добавляется рекомендация «что можно сделать», например
  сколько часов роли не хватает или на сколько спринтов сдвинуть задачу.

## KPI (backend/kpi/metrics.py)

- Квартал = 6 спринтов по 2 недели; «в течение 12 недель» = окончание не позже 6-го спринта.
- Знаменатели берутся только из `Plan.baseline` и при пересчёте не меняются:
  PI — число PRODF, у которых в baseline есть задачи с `decision="included"`;
  Say/Do — SP задач baseline с `planned_end == N`.
- Процент выполнения квартального плана считается в двух срезах с общим
  знаменателем (инициативы, взятые в квартал на Неделе 0):
  `scope="committed"` — закрыты ли задачи, которые взяли в квартал (обещание
  команды); `scope="initiative"` — закрыты ли ВСЕ задачи инициативы, включая
  перенесённые (обещание бизнесу, цель достигнута целиком).
  Первый срез отвечает на вопрос «сделали ли то, что обещали», второй — «достигли
  ли цели». Показывать нужно оба: иначе метрика даёт 100 % в ситуации, когда
  в квартал взята лишь малая часть задач.
- Частично достигнутые цели описываются справочником «Варианты выбора цели»
  (`target_option` в задаче), например «3. Функционал реализован частично».
- Задачи, добавленные после Недели 0, на этот KPI не влияют.
- Задача, растянутая на несколько спринтов, засчитывается в Say/Do целиком
  в спринт окончания (план — по `planned_end` baseline, факт — по `actual_end`).
- В числитель Say/Do идут все задачи, фактически завершённые в спринте,
  включая не запланированные на него изначально.
- Прогноз отделён от факта: `pi_predictability(..., mode="fact")` — только Done,
  `mode="forecast"` — Done или прогноз окончания (`forecast_end`, иначе `planned_end`) ≤ 6.
- Задача в статусе Done без `actual_end` считается завершённой в срок.
- Пустой знаменатель → KPI = 0.0.
- Колонка «итоговый результат» в числитель PI не входит: в формуле условия —
  «завершённых», а не «успешно завершённых» (как в PDF-онбординге).

## Причины решений (backend/explainability/reasons.py)

- Причина обязательна для каждого решения, включая `included`.
- Для переноса/отмены используется справочник датасета «Причины расхождения
  планов заказчика и исполнителя» (5 кодов), итог — из «Вариантов выбора цели».
- Для включения — собственный справочник `InclusionCode`.

## Пересчёт плана (backend/recalculation/)

- Квартал календарный: старт 01.07.2026 (ответ экспертов), 6 спринтов по 14 дней,
  последний день — 22.09.2026 (`quarter.py::QUARTER_START`).
- Часы задачи — из калькулятора сметы по ролям (ответ экспертов: калькулятор — целевая
  смета); строка «Итого по ролям» и нулевые ячейки отбрасываются. Потрачено — из
  Spent_time_roles. Остаток роли = смета − потрачено, не меньше нуля.
- baseline фиксируется один раз независимой копией и больше не меняется; повторная
  фиксация — ошибка.
- Факт принимается строго по одному спринту и по порядку: пропустить спринт или
  подать тот же спринт повторно нельзя — система не видит будущего (защита от утечки).
- При пересчёте Done-задачи и прошедшие спринты заморожены; незавершённые задачи
  перепланируются с `sprint + 1` тем же планировщиком, что строил план Недели 0,
  на остаток часов. Остаток SP — пропорционально остатку часов.
- Задачи, отложенные на Неделе 0, при пересчёте тоже пробуются снова: если освободилась
  ёмкость, они могут войти в квартал.
- В исходных данных нет факта внутри квартала, поэтому факт для демо генерируется
  сценариями из самого плана; задача/инженер для сценария выбираются по структуре
  плана, а не по зашитым id — сценарии работают на любом датасете того же формата.
- Колонки-«ответы» Tasks (`будет включено в спринт`, `исполнитель`, `итоговый результат`)
  и старые плановые даты из Excel в пересчёте не используются.

## Риски (backend/risk/)

- Красный: прогноз окончания > 6-го спринта или задача из baseline выпала из квартала.
  Отложенное на Неделе 0 — решение планировщика, а не риск.
- Жёлтый: сдвиг считается относительно baseline (держится, пока задача заканчивается позже
  обещанного); алерт — на исходную задачу цепочки. Все три типа связей — «A блокирует B».
- Оранжевый (как в условии): потребность роли на следующий спринт = остаток часов /
  оставшиеся спринты задачи (равномерно), по всем задачам плана; фонд — `80 × capacity_rate`
  по всем сотрудникам роли в компании (планировщик берёт людей из общего пула).
  Роли, которых нет ни у одного инженера компании, — один алерт «нанять» на роль.
- Названия ролей сравниваются без регистра и пробелов («ДевОпс»/«Девопс», «Big Data»/«BigData»).
- Задачи-призраки и прочие ошибки таблиц не исправляются, а выносятся в отчёт о
  качестве данных (ответ экспертов).
- «Нанять» рекомендуется, если роли нет в компании **или** свободных часов этой роли у других
  команд до конца квартала меньше, чем нужно («есть, но все заняты»). Иначе — «привлечь» с
  конкретным инженером и его свободными часами. Свободные часы = фонд инженера минус часы,
  которые план уже отвёл ему по спринтам.
- «Закреплённых» за проектами инженеров не вводим: в данных этого нет, а ручной список
  позволял бы подгонять дефицит. Возможное развитие — флаг в профиле инженера.
- Задача, у которой остаток SP больше ёмкости команды за спринт, начаться не может —
  об этом отдельный алерт с советом разбить её на части.
- План Недели 0 и пересчёт строятся одним шагом (`recalc.plan_tasks`): задачи в работе —
  на остаток часов и пропорциональный остаток SP, задачи без сметы откладываются с причиной
  «Не оценивалась», отменённые заказчиком не планируются, а зависящие от них задачи не могут
  начаться.
- Отменённая задача из baseline — красный алерт (обещание Недели 0 не выполнено), в KPI она
  остаётся в знаменателе. Новые задачи, добавленные в квартале, в baseline и KPI не входят.
- Кадровые решения не мгновенны: найм ≈ 3 спринта (6 недель), переключение инженера из
  другой команды ≈ 1 спринт (`quarter.py`, меняется в одном месте). Если к моменту выхода
  человека задачу уже не успеть закончить к 12-й неделе, рекомендуется перенос в следующий
  квартал с подготовкой найма к его старту (01.10.2026, поиск — не позже 20.08.2026).
- Длительность отложенной задачи для оценки сроков — по самой большой роли при одном
  человеке на роль (80 ч за спринт).
- Новый сотрудник выходит на полную продуктивность не сразу: 1-й спринт — 50 %, 2-й — 75 %,
  дальше 100 % (`quarter.py::ONBOARDING_RAMP`); переключённый из другой команды — 75 % в
  первый спринт (`BORROW_RAMP`). Планировщик принимает одну ёмкость инженера на все спринты,
  поэтому нанятому даётся средняя продуктивность по оставшимся спринтам (суммарные часы
  точные, распределение уточняется при каждом пересчёте). Развитие — ёмкость по спринтам
  в планировщике.
- В сценарии «Нанять роль» и в «что если нанять» нанятый работает со следующего спринта
  (без срока поиска, но с адаптацией) — это оценка потолка эффекта; реальные сроки с поиском
  и адаптацией показывают рекомендации алертов.
- Руководитель может перенести задачу в следующий квартал: на Неделе 0 (`defer=`) — это
  меняет baseline и алертом не считается; в квартале (факт `defer`) — красный алерт для
  задачи из baseline. Перенесённая задача получает цель «не будет взято в квартал» (или
  «3. Функционал реализован частично», если работы начаты), её можно вернуть.
- Бэклог следующего квартала группирует перенос по причинам и даёт действия к старту:
  нанять (с датой начала поиска), разбить крупные задачи, оценить неоценённые.
- KPI: задачи, закрытые до Недели 0, в знаменатель PI Predictability не входят — планировщик
  помечает их `included` в спринт 0, но по ответу экспертов Done в квартал не берутся.

## Проверка устойчивости (22.09.2026)

Ревью корректности пересчёта, логики рисков, стыков модулей и устойчивости — исправлено:
- Оранжевый «дефицит роли» считается по фонду всей компании (планировщик берёт людей из
  общего пула); «нанять» — только для ролей, которых нет в компании, один алерт на роль.
- Рекомендации «привлечь» расходуют общий пул свободных часов — один человек не
  предлагается нескольким командам; отсчёт — со спринта, когда он может переключиться.
- Жёлтый держится, пока задача заканчивается позже, чем в baseline (раньше «решался» на
  следующем спринте); красный показывает корневую причину по цепочке блокеров.
- Недоступный инженер остаётся в расчёте с нулевой ставкой — роль не считается
  «отсутствующей в компании».
- После 6-го спринта незакрытые задачи получают честную причину «квартал завершён,
  остаток переходит» (а не «ждёт смежную команду»).
- Факт: роли с разным написанием сводятся к написанию сметы; статусы-синонимы
  («Выполнено», «Готово», «Closed»…) распознаются, неизвестные — предупреждение; часы с
  запятой; новые задачи обрабатываются раньше фактов.
- «Что если нанять» и план найма учитывают срок поиска (выход к спринту 4) и адаптацию.
- Сценарии выбирают цель с видимым эффектом: задержка — задача с цепочкой задач плана;
  уход/отпуск — единственный носитель роли; найм — роль, которой нет в компании.
- Отчёт `run_quarter` целиком сериализуется в JSON; неверная папка данных — ошибка.
- Отчёт о качестве данных дополнен циклами и самоссылками в зависимостях.

## Вторая волна: планировщик, данные организаторов, поток загрузки (22.09.2026)

- **Роли без людей → частичная цель.** Строгое правило «нет Руководителя проекта — задачу не
  берём» оставляло в квартале 10 задач из 37 и пустые 5–6 спринты. По ответу экспертов
  («рекомендация… частичная цель из Вариантов выбора цели») работа доступных ролей
  планируется, недостающие часы — в дефицит, цель: нет только руководителя/поддержки →
  «4. Функционал реализован и готов к ИТ», иначе → «3. … частично». Больше 50% сметы на
  недостающие роли — перенос. Так же, если роль есть, но её часы до конца квартала заняты.
  Итог: 36 из 37 задач, ёмкость команд по SP загружена до лимита. Строгий режим оставлен.
- **SP по спринтам пропорционально часам** — задача крупнее спринтовой ёмкости растягивается.
- **Люди из других команд** берутся, когда свои заняты (не только когда роли в команде нет);
  парттаймер отдаёт каждой своей команде только её долю.
- **Стек** — технология из названия задачи ограничивает круг носителей роли.
- **Устойчивость пересчёта**: хвост SP считается без ролей в дефиците, доля недостающих ролей —
  от полной сметы, очередь прошлого плана сохраняется. Без отклонений пересчёт воспроизводит
  собственный план (ноль сдвигов за 6 спринтов).
- **Датасет организаторов** `Хакатон_датасетс_правками_по_списку_вопросов_1.xlsx` — источник по
  умолчанию; в нём нет задач-призраков и дубля связи, 19 зависимостей. Парсер ищет конец
  таблицы по ближайшему маркеру, шапку зависимостей отбрасывает по содержимому, требует
  обязательные колонки, читает числа с запятой, лог исключённых связей пишет всегда.
- **Поток загрузки факта**: файл спринта — датасет с накопленными часами; при загрузке
  вычитается уже учтённое (`fact_from_dataset_excel`). Демо-факты генерируются из симуляции
  по плану (`sprint.py`), поэтому «идеальный» сценарий действительно без отклонений.
- **Звёздная карта**: Bus Factor внутри команд, «нанять» (роли с BF = 0, с кандидатом из смежной
  роли) и «обучить» (кандидат уже знает ключевой стек роли или ≥ 2 навыка носителя).
- **KPI**: пустые и будущие спринты — «нет данных»; знаменатель PI зафиксирован на Неделе 0,
  отменённые заказчиком инициативы выводятся отдельным списком.
