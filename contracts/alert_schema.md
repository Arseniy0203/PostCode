# Схема Alert

Ответственный: Человек 2 (recalculation + risk). Код: `backend/risk/alerts.py::Alert`,
в UI отдаётся через `Alert.to_dict()`.

| Поле               | Тип                                        | Описание |
|--------------------|--------------------------------------------|----------|
| type               | Literal["red", "yellow", "orange", "info"] | Цвет/важность. red/yellow/orange — обязательные по условию, info — дополнительные |
| category           | str                                        | `critical` (red) / `cascade` (yellow) / `resource`, `hiring`, `capacity` (orange) / `blocked`, `overrun`, `stale`, `kpi`, `single_point`, `data_quality` (info). Ключ жизненного цикла: для resource/hiring/single_point — роль, для остальных — задача |
| task_id            | str                                        | Задача, породившая алерт (для orange — самая «тяжёлая» задача роли) |
| prodf_id_at_risk   | str                                        | Инициатива под риском. Обязательно для red/yellow/orange; у data_quality может быть `""`, если обе задачи — призраки |
| description        | str                                        | Что случилось, с цифрами и датами спринтов |
| recommendation     | str                                        | Что можно сделать (ответ экспертов: к переносу добавлять рекомендацию) |
| sprint_detected    | int                                        | Спринт пересчёта, на котором обнаружен (0 — Неделя 0) |
| team_id            | str \| None                                | Команда |
| role               | str \| None                                | Роль — только для orange |
| deficit_hh         | float \| None                              | Дефицит часов — только для orange |
| affected_task_ids  | list[str]                                  | Все задействованные задачи (для yellow — вся цепочка) |
| affected_prodf_ids | list[str]                                  | Все задействованные инициативы |
| defer_task_ids     | list[str]                                  | Для hiring/capacity: задачи, которые не успеть в квартале даже с наймом/переключением — предлагается перенос |
| status             | str                                        | `new` — появился в этом спринте, `ongoing` — висит с `since_sprint` |
| since_sprint       | int \| None                                | С какого спринта алерт держится |

Решённые алерты (были в прошлом спринте, пропали в этом) лежат отдельно в
`plan["resolved_alerts"]` / `history[i]["resolved_alerts"]` со `status="resolved"` и `resolved_sprint`.

Сортировка (`collect_alerts`): red → yellow → orange → info, затем по инициативе.

## Правила генерации

- **red / critical** — прогноз окончания задачи (`forecast_end_sprint`) > 6-го спринта, **или**
  задача была `included` в baseline, а при пересчёте стала `postponed`. Задачи, отложенные
  сразу на Неделе 0, алертом не считаются — это решение планировщика, а не отклонение.
- **yellow / cascade** — задача заканчивается позже, чем в baseline, и от неё зависят
  незавершённые задачи плана. Алерт держится, пока сдвиг против baseline не исчез; если с
  прошлого пересчёта сдвиг вырос, в тексте «С прошлого пересчёта — ещё +N». Алерт ставится на
  исходную задачу цепочки, в `affected_task_ids` — вся цепочка. Все три типа связей — «A
  блокирует B». Если задачу закрыли с опозданием, алерт держится («задача закрыта с
  опозданием»), пока зависимые от неё задачи идут позже baseline.
- **orange / resource** — как в условии: потребность роли на следующий спринт больше фонда часов
  **всех** сотрудников этой роли в компании (`80 × capacity_rate`). Потребность = часы роли в
  этом спринте по раскладке плана (`allocation`; без неё — остаток / оставшиеся спринты) плюс
  часы задач, отложенных из-за нехватки часов. Алерт — только если у роли есть работа в спринте
  и люди в компании (роль без людей — это hiring); допуск на округление 0.05 ч.
- **orange / hiring** — один алерт на **роль**, которой нет ни у одного инженера компании:
  задачи с частичной целью (часы роли в дефиците) и отложенные задачи, часы по командам,
  «нанять или обучить», сроки: какие частичные задачи с наймом (выход к спринту 4) успеют до
  полной цели, какие отложенные успевают / не успеть — перенос.
- **orange / capacity** — задача отложена, хотя все роли в компании есть: (а) её SP больше
  ёмкости команды за спринт — совет разбить на части или частичная цель; (б) часы ролей заняты —
  «привлечь ENG-… из Team-… (N ч)» из **общего пула свободных часов** (один человек не
  предлагается нескольким командам на одни и те же часы; отсчёт — со спринта, когда он может
  переключиться; если он единственный носитель роли — предупреждение про Bus Factor) или
  «нанять», если свободных часов до конца квартала не хватает («в компании N чел., но …»).
  Если задача не влезла по SP команды (`PLAN_EXCEEDED`) — совет освободить ёмкость команды или
  частичная цель, а не «привлечь людей». Отдельный алерт — задача идёт с частичной целью, потому
  что часы существующей роли заняты: кого привлечь или нанять, чтобы довести до полной цели.
- **Сроки в рекомендациях hiring/capacity.** Найм ≈ 3 спринта, переключение из другой команды
  ≈ 1 спринт (`quarter.py`: `HIRE_LEAD_SPRINTS`, `BORROW_LEAD_SPRINTS`). Длительность задачи —
  по самой большой роли при одном человеке на роль; «начать не позже» = 6 − длительность + 1.
  Текст: «успевают при найме (человек начнёт работать: спринт 4): …; не успеть в квартале: … —
  перенести в следующий квартал (01.10.2026) и начать подготовку сейчас».
- **info / blocked** — задача отложена, потому что не входит в квартал её блокирующая задача;
  цепочка до корневой причины («ждёт MP-102 → DB-202, корень — …»). Инвариант: у каждой
  отложенной задачи есть хотя бы один алерт с объяснением.
- **info / overrun** — по роли потрачено больше, чем заложено в калькуляторе сметы.
- **info / stale** — задача InProgress начата > 8 недель до старта квартала и не движется,
  или по ней нет прироста часов 2 спринта подряд.
- **info / kpi** — прогноз PI Predictability < 80% (список не успевающих инициатив) или
  Say/Do только что прошедшего спринта вне 90–105%. Считается через `backend/kpi/metrics.py`.
- **info / single_point** — один алерт на инженера, который единственный в компании носитель
  роли, нужной задачам плана (Bus Factor роли = 1). Это риск плана по ролям; Bus Factor по
  навыкам (skills_declared) — звёздная карта, `backend/starmap/`.
- **info / data_quality** — `backend/risk/data_quality.py::check_data_quality`: задачи-призраки
  в зависимостях и в калькуляторе, дубли связей, `estimated_hh` в Tasks ≠ калькулятор.

## Для UI: одна функция

```python
from backend.recalculation.pipeline import run_quarter
report = run_quarter("key_task_delay", until_sprint=3)   # 0 — только Неделя 0
```

`report`: `alerts` (dict), `resolved_alerts`, `by_prodf` (сводка по инициативам: `worst`,
`headline`, `counts`, `causes`, `recommendations`), `history` (по спринтам: `fact`, `changes`,
`alerts`), `data_quality`, `hiring` (`options[].headline` — «Нанять в Team-X: … → +N задач»,
`ceiling`), `hiring_roadmap` (жадный план найма: `headline` — «1. Нанять «…» в Team-X → +N
задач»), `summary` (что взято в квартал в baseline и сейчас), `quarter_summary` (итоги по
задачам и инициативам: `done` / `on_plan` / `carry_over` / `not_in_quarter` / `cancelled`,
до 6-го спринта — прогноз; `deferred` — перенесена руководителем), `next_quarter`
(бэклог следующего квартала: `tasks[]` с `kind` — `manual` / `no_role` / `oversized` /
`blocked` / `not_estimated` / `capacity` / `carry_over`, и `prepare[]` — что сделать к старту:
`hire` с датой «начать поиск не позже», `split`, `estimate`), `kpi`, `scenarios`, `plan`.
Также: `starmap` (звёздная карта, `starmap_schema.md`), `strict_comparison` (что взяли бы по
строгому правилу «нет роли — не берём»), `sprints` (даты сетки), `dependencies`.
Параметры: `missing_roles="partial" | "postpone"`, `facts=[...]` — загруженные факты.
Сценарии: `on_track`, `key_task_delay`, `engineer_leave`, `vacation`, `early_finish`,
`hire_role`, `defer_task`; `target=` — ручной выбор задачи/инженера/`{"team_id","role"}`.
Перенос на Неделе 0: `run_quarter(..., defer=["KP-0000"])` или `{"KP-0000": "комментарий"}`.

Факт спринта (`apply_sprint_fact`): по задаче — `status` (`Done` / `InProgress` / `Cancelled` /
`Deferred`), `spent_hh` (часы за спринт), `estimated_hh` (переоценка), `defer` (`true` —
перенести в следующий квартал, `false` — вернуть), `note`; на уровне спринта —
`tasks_added`, `engineers_unavailable`, `engineers_returned`, `engineers_hired`.
Ошибочный факт отменяется `rollback(plan, sprint)`. Факт из Excel:
`load_fact_excel(path)` → `apply_uploaded_fact(plan, data, fact)`.

Поток интерфейса «загрузить датасет → загрузить файл спринта» (frontend/app.py):
`week0_from_excel(bytes)` — план Недели 0 тем же конвейером (ключи `parsed`, `clean_deps`,
`plan`, `alerts`, `starmap`, `report`); `fact_from_dataset_excel(bytes, plan)` — файл в формате
датасета с **накопленными** часами (как `demo_scenarios/`, генерирует `sprint.py`) → факт за
спринт: уже учтённые часы вычитаются, статус передаётся, только если изменился.

## Где лежат алерты в плане

После `apply_sprint_fact`: `plan["alerts"]` — список `Alert` последнего пересчёта,
`plan["history"][i]["alerts"]` — алерты каждого спринта в виде dict,
`plan["history"][i]["changes"]` — что поменялось в плане и почему.
